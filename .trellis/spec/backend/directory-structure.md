# Backend Directory Structure

## Runtime boundaries

The backend runs from `backend/`; commands and imports assume that directory is
the working directory. `backend/main.py` owns the Typer commands
(`run` / `revision` / `upgrade`) and constructs the FastAPI application through
`backend/app/__init__.py:create_app()`.

`backend/app/__init__.py` is the app factory and lifecycle owner. It defines
`lifespan()` plus `register_exceptions`, `register_middlewares`,
`register_routers`, `register_static`, `register_docs`, and `register_frontend`,
and calls them in that order from `create_app()`. There is **no
`backend/app/init_app.py`**; references to that path in older notes are stale.

```text
backend/
├── main.py                 # run/revision/upgrade CLI and app factory entry
├── alembic.ini             # Alembic configuration
├── pyproject.toml          # dependencies and Ruff/pytest config
├── app/
│   ├── __init__.py         # create_app(), lifespan(), register_* functions
│   ├── api/
│   │   └── v1/             # __init__.py + routers.py only (route registry)
│   ├── common/             # response envelopes, enums, shared data objects
│   ├── config/             # settings and filesystem paths
│   ├── core/               # DB/session, auth, CRUD, middleware, logging, plugins
│   ├── modules/            # first-party business code (<area>/<feature>)
│   ├── plugin/             # dynamically discovered extension modules
│   ├── scripts/            # initialization routines (seed + migration bootstrap)
│   ├── utils/              # reusable, mostly stateless helpers
│   └── alembic/            # migration environment and versions
├── templates/              # {python,ts,vue}/*.jinja2 code-generation templates
├── sql/                    # flat *.json seed data (menu/role/user/dept/dict/…)
├── data/                   # bundled data (e.g. ip2region)
├── static/                 # static assets and local upload root
├── logs/                   # fastapiadmin.log and rotated archives
├── dist/                   # optional built web app served by register_frontend
└── tests/                  # pytest fixtures and tests
```

`app/api/` deliberately contains only `__init__.py` and
`v1/{__init__.py,routers.py}`. First-party business code does **not** live under
`app/api/v1/`.

## Business slices

First-party features are vertically sliced as
`backend/app/modules/<area>/<feature>/`, where `<area>` is one of
`ai`, `common`, `generator`, `monitor`, `system`, `task`. A full data-backed
slice normally contains:

- `controller.py`: FastAPI boundary only—typed request inputs, permission and
  DB dependencies, response model, and `SuccessResponse`.
- `service.py`: business rules, orchestration, output-schema conversion, and
  `CustomException` decisions.
- `crud.py`: a small feature-specific subclass of
  `backend/app/core/base_crud.py:CRUDBase`; add direct SQL only when the base
  operations cannot express the query.
- `model.py`: SQLAlchemy 2.0 mapped model.
- `schema.py`: Pydantic request, query, and output schemas.

`backend/app/modules/system/dept/` demonstrates the complete flow. A feature
without persistence may omit `crud.py` and `model.py`; examples include the
health and monitor subdomains. Do not create empty layers merely to match the
template. Feature packages also carry an `__init__.py`; a module-level
`__init__.py` may be generated by the code generator (see below).

## Route registration

`backend/app/api/v1/routers.py` is the **single route fact source**. It imports
every first-party controller and assigns them to the explicit
`DOMAIN_CONTROLLERS: dict[str, list[APIRouter]]` table keyed by domain prefix:

| Prefix | Domain |
|---|---|
| `/system` | auth, user, role, menu, dept, position, dict, params, notice, ticket, version, log |
| `/monitor` | cache, health, online, server |
| `/task` | cronjob job/node, storage browse/node/transfer/workflow |
| `/ai` | chat |
| `/generator` | gencode |
| `/common` | file |

`backend/app/__init__.py:register_routers` includes `api_v1` from this table and
then calls `app/core/discover.py:dynamic_router.init_app(app)` for plugins.
There are no per-area `module_<area>/__init__.py` router assemblies and no
manual plugin-router imports.

## Controllers and dependencies

Use an `APIRouter` with `route_class=OperationLogRoute`. Declare inputs with
`Annotated` and FastAPI's `Body`, `Path`, `Query`, `Depends`, or `Security`.
Authenticated endpoints inject both `AuthSchema` through `AuthPermission` and
`AsyncSession` through `db_getter`. Always declare `response_model` using
`ResponseSchema[...]`, including `ResponseSchema[None]` for empty success data.

Keep controllers thin.
`backend/app/modules/system/dept/controller.py` constructs
`DeptService(auth, db)`, delegates once, and returns `SuccessResponse`; it does
not contain uniqueness checks, tree traversal, or SQL.

## Permission identifiers

Permission strings use the `模块:资源:操作` shape with a `module_` prefix, for
example `module_system:dept:query`, `module_ai:chat:create`, or
`module_monitor:dashboard:query`. They are passed to `Security`:

```python
Security(AuthPermission(["module_system:dept:query"]))
```

Backend code only ever uses the `module_<area>:<resource>:<action>` form;
there are no `sys:*` literals in the codebase. When adding an endpoint, derive
the identifier from the area and feature, not from an older example.

## Plugins

Extension code belongs below `backend/app/plugin/` in a `module_<name>` directory,
not inside a first-party area. `backend/app/core/discover.py` scans
`app/plugin/module_*/**/controller.py`, imports top-level `APIRouter` instances,
and maps `module_example` to the `/example` container prefix. Every import-path
segment must be a valid Python identifier and should contain `__init__.py`.

Discovery is **startup-only and fail-fast**:

- An unimportable plugin or controller raises `RuntimeError` and aborts startup.
  A half-built router would otherwise serve a process with missing endpoints,
  turning a clear failure into a mysterious per-module 404.
- `check_route_conflicts()` also halts startup when the same method+path is
  registered twice (parameter names are normalized before comparison).

Because discovery never re-runs, creating or generating a module requires a
**backend restart** to become reachable. Development reload does not re-run
discovery, so a new module silently 404s until the process restarts.

`plugin.toml` is optional metadata and does not install dependencies. It sits at
the **area/package level** (for example `backend/app/modules/system/plugin.toml`,
`backend/app/plugin/module_example/plugin.toml`) and is present for first-party
areas too; runtime discovery ignores it. Its fields are `name`, `title`,
`version`, `description`, and optional flags/tags.

Use `backend/app/plugin/module_example/demo/` as the structural example.

## Code generation

The generator lives in `backend/app/modules/generator/gencode/` and renders
Jinja2 templates from `backend/templates/{python,ts,vue}/*.jinja2` (registered
templates include feature-level `controller/service/crud/schema/model/__init__`
plus `package_init.py.jinja2` and `plugin.toml.jinja2`). Generated output is
written under `app/modules/` (or `app/plugin/`) and still must be reviewed.
After generating or modifying code you **must restart the backend** for
discovery and routing to pick it up. See
`../architecture/code-generation-and-routing.md` for the full contract.

## Frontend static hosting

`register_frontend` (`backend/app/__init__.py`) mounts the built web app only
when `path_conf.FRONTEND_DIST_DIR` (`backend/dist`) exists; it passes
`check_dir=False`. The existence check and the mount must use the **same**
`FRONTEND_DIST_DIR`. If they diverge, the app registers but fails only on the
**first request** to `/`, and the reason is visible only in
`backend/logs/fastapiadmin.log`.

## Naming and placement

- Python modules and directories use `snake_case`; first-party areas under
  `app/modules/` do **not** use a `module_` prefix. Only `app/plugin/`
  directories use `module_<name>`.
- Mapped classes, services, schemas, and CRUD classes use `PascalCase` plus the
  local suffix (`DeptModel`, `DeptService`, `DeptOutSchema`, `DeptCRUD`).
- Router variables use the feature name plus `Router` (`DeptRouter`).
- Put cross-feature framework behavior in `app/core/`; put shared protocol
  objects such as response envelopes and enums in `app/common/`; keep generic
  transformations in `app/utils/`.

`app/core/` currently houses `database.py`, `base_crud.py`, `base_model.py`,
`base_schema.py`, `redis_crud.py`, `security.py`, `permission.py`,
`dependencies.py`, `exceptions.py`, `router_class.py` (`OperationLogRoute`),
`ap_scheduler.py`, `sse_manager.py`, `middlewares.py`, `logger.py`,
`validator.py`, and `discover.py`.

Avoid business-specific helpers in `app/core/` or `app/utils/`, controllers
that execute SQL directly, manual imports of plugin routers, and new top-level
backend packages that bypass the existing app factory.
